Concurrency-safe by design, not by luck

Two people book the same slot. Only one should win.

A room booking app for FAU Erlangen-Nürnberg study rooms and seminar spaces, built around one real concurrency bug. Found it under load, fixed it two different ways, and load-tested both until the numbers proved which one held up.

The bug

Check-then-insert isn't atomic

Two requests can both check "is this slot free?", both get "yes," and both insert, because nothing ties the check to the write.

Naive: check, then insert

request A
SELECT: free INSERT
request B
SELECT: free INSERT

B's check runs before A's insert lands, so both see an empty slot and both write. Two overlapping bookings, both "successful."

Fixed: a database constraint

ALTER TABLE bookings
  ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (
    resource_id WITH =,
    tstzrange(start_time, end_time) WITH &&
  );

Postgres itself rejects the second row at commit time. No application code has to remember to check anything. A row-lock alternative was tried first; it worked too, but serialized every booking on a resource, not just conflicting ones.
